Publishing Wizard

A guided path from “two signed AABs on my laptop” to “published”. Tick the boxes as you go — this page remembers your progress (stored only in your own browser).

What you already have (from the repo, all verified): signed release bundles via ./build_paid.sh and ./build_free.sh, sideload APKs via --apk, listing copy + data-safety answers in STORE_LISTING.md, and this site's privacy policy to use as the required public URL.

Part 0 — Before anything

Back up release.keystore off this computer

Copy android/app/release.keystore (plus the passwords in android/local.properties) to at least two safe places — an encrypted USB stick and a password manager note, for example. If this file is lost, neither app can ever be updated again.

Host this site somewhere (gives you the privacy-policy URL Play requires)

These four files (index.html, privacy.html, publish-guide.html, soundwalk-1bit.png) are a complete static site — all links are relative, so drop them on any web host and they work. What Play Console actually needs is a public URL for privacy.html.

Free / cheap options that host a plain folder of files:

  • Netlify Drop — app.netlify.com/drop: literally drag the folder onto the page; instant URL, no account needed to try.
  • Cloudflare Pages — free, upload the folder or connect a repo.
  • Codeberg Pages — free static hosting for public repos, no cost, fits the ethos.
  • GitHub Pages — free for public repos (repo Settings → Pages → branch main, folder /docs). Only private repos need a paid plan.
  • Your own web space — e.g. under the etc.altred.xyz domain: upload the folder via FTP/SFTP.

Once hosted, note the full URL of privacy.html (for example https://etc.altred.xyz/soundwalk/privacy.html) — that's the privacy-policy URL Play Console asks for, and the one to paste into STORE_LISTING.md. Then update the four store/donation links in index.html once those exist.

Part 1 — Google Play developer account

Create the developer account (US$25, one time)
  1. Go to play.google.com/console/signup and sign in with the Google account you want to own the apps (use one you will keep long-term).
  2. Choose “Yourself” (personal account) unless you have a registered organization. Pay the US$25 one-time fee.
  3. Complete identity verification (government ID + address). This can take from hours to a few days — start it early.
Understand the closed-testing requirement (plan for it!)

Important: new personal developer accounts must run a closed test — a group of testers (Google has required 12–20; the Console shows your exact number) who opt in and keep the app for 14 continuous days — before you can apply for production (public) access.

This is actually an opportunity: recruit testers from the MANAKAI community, students, and fellow artists. They only need a Gmail address and an Android phone. Fourteen days of real soundwalks is also excellent field testing.

Set up the payments profile (only needed for the paid app)

To charge money for the full version, Play Console → Setup → Payments profile → create a Google Payments merchant account (supported for sellers in Colombia). You'll enter tax/bank details; Google pays out monthly. You can postpone this: publish the free app first, add the paid one when the merchant profile is ready. (Google's service fee is 15% for the first US$1M/year once you enroll in the 15% tier.)

Part 2 — The Free app first (easier, no payments)

Do the free app first: it exercises the whole pipeline without the merchant setup, and it's the one for the closed test.

Create the app in Play Console
  1. Play Console → Create app.
  2. Name: SoundWalk Free · default language: English (US) — you'll add Spanish as a translation. App (not game) · Free.
  3. Accept the declarations and create.
Fill “App content” (the compliance checklist)

Console sidebar → Policy → App content. Work through each item — all the answers are already written in STORE_LISTING.md:

  • Privacy policy: https://alejoduque.github.io/BioMapp/privacy.html
  • App access: “All functionality is available without special access” (no login).
  • Ads: No ads.
  • Content rating: fill the IARC questionnaire honestly (no violence/sex/gambling/user chat) → rating “Everyone”.
  • Target audience: choose 13 and older. (Selecting under-13 triggers the much stricter Families program — not needed; teens + adults covers the community use.)
  • News app: No. COVID app: No. Government app: No. Financial features: None.
  • Data safety: declare that no data is collected or shared — mic and location are processed on-device only, never transmitted. Deletion = in-app delete or uninstall. (Exact wording in STORE_LISTING.md.)
Create the store listing (EN + ES)
  1. Grow → Store presence → Main store listing: paste title, short and full description from STORE_LISTING.md (FREE — English).
  2. Add a translation: Manage translations → Spanish (Latin America) and paste the DerivaSonora Free texts.
  3. Upload assets: 512×512 icon, 1024×500 feature graphic, and at least 2 phone screenshots per language. Phone screenshots of the real app are fine (landing, map with markers, recorder with species chips, player).
Upload the AAB to Internal testing
  1. Build fresh: ./build_free.sh → produces soundwalk-free-2.3.0-*.aab.
  2. Test and release → Testing → Internal testing → Create new release. When asked, accept Play App Signing (Google holds the app signing key; your keystore becomes the upload key — this protects you if the keystore is ever lost after enrollment).
  3. Upload the .aab, add release notes (one line is fine), save.
  4. Add your own Gmail to the internal testers list, open the opt-in link on your phone, and install from Play. If this works, the whole signing pipeline is proven.
Run the closed test (the 14 days)
  1. Testing → Closed testing → Create track, promote the internal release into it.
  2. Create an email list of testers (Gmail addresses) and share the opt-in link. You need the number shown in your Console (12–20) opted in.
  3. Keep the test running 14 continuous days. Encourage real use — soundwalks, imports, both languages.
  4. When Console shows the requirement met, click Apply for production access and answer the short questions about your testing.
Publish Free to production
  1. Production → Create new release → promote the tested release.
  2. Select countries (all, or start with the Americas + Spain).
  3. Submit for review. First reviews typically take 1–7 days.
  4. When live, copy the real store URL (https://play.google.com/store/apps/details?id=com.soundwalk.recorder.free) into docs/index.html, replacing the placeholder.

Part 3 — The Paid app

Create “SoundWalk” (paid) and set the price
  1. Requires the merchant/payments profile from Part 1.
  2. Create app → name SoundWalk → Paid.
  3. Repeat the same App content + store listing steps (use the PAID texts in STORE_LISTING.md).
  4. Build with ./build_paid.sh, upload soundwalk-paid-2.3.0-*.aab, test internally, then release.
  5. Monetize → Products → App pricing: set the price (you can change a price later; you can make a paid app free later, but never free → paid).
  6. When live, update the Play links in docs/index.html and the upgrade deep-link already baked into the free app will resolve (market://details?id=com.soundwalk.recorder).

Note: your account being new, the paid app may also need its own closed-testing period — the Console will tell you. The same tester group can be reused.

Part 4 — Gumroad (sell the APK directly, no store)

Set up a Gumroad product for the full APK

Gumroad lets you sell the full-version APK directly — aligned with the permacomputing/artist-economy spirit, no store review, and buyers anywhere Play doesn't reach. It complements (not replaces) the Play listing.

  1. Create an account at gumroad.com (payouts to Colombia work via PayPal — connect it in Settings → Payments; check their current fee, roughly 10% + payment costs).
  2. New product → Digital product. Name: “SoundWalk — full version (Android APK)”. Upload soundwalk-paid-2.3.0-*.apk (the --apk build, not the .aab — only APKs can be installed directly).
  3. Price it (Gumroad also supports “pay what you want” with a minimum — a nice fit for community distribution).
  4. In the product description, include sideloading instructions: “Download on your Android phone → open the file → allow ‘install unknown apps’ when prompted → install.”
  5. Copy the product URL into docs/index.html.

Trade-off to know: Gumroad buyers don't get automatic updates — when you release a new version, upload the new APK to the product and use Gumroad's “email customers” feature. Also keep the APK version identical to the Play one so both install bases stay in sync.

Part 5 — Ko-fi (support the work)

Set up Ko-fi
  1. Create a page at ko-fi.com — one-off donations are fee-free on Ko-fi's side (only PayPal/Stripe processing fees; check current terms).
  2. Write a short bio connecting the app to the research: soundwalks, bioacoustics, MANAKAI, youth conservation. People support stories, and this one is genuinely good.
  3. Optional: Ko-fi Shop can also deliver the APK as a digital download, or a membership tier can offer early builds — an alternative or complement to Gumroad.
  4. Copy your Ko-fi URL into docs/index.html.

Part 6 — After launch

Replace all placeholder links on the site

Edit docs/index.html: swap the four href="#" placeholders for the real Play, Gumroad and Ko-fi URLs and remove the class="soon" / ⏳ marks. Commit and push — Pages redeploys automatically.

Releasing updates
  1. Bump versionCode/versionName in android/app/build.gradle (scheme: MAJOR*10000 + MINOR*100 + PATCH) and VERSION.
  2. ./build_free.sh and ./build_paid.sh → upload both AABs to their Console tracks.
  3. Update the Gumroad APK + notify customers.
  4. Add a CHANGELOG entry.

Aside — why not F-Droid?

F-Droid would fit the permacomputing ethos, but it requires a free/open-source license and the code is CC BY-NC-SA (the NonCommercial clause disqualifies it). If you ever relicense (e.g. AGPL), F-Droid becomes an option.
